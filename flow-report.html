Summary

RealTemp is correctly shaped as a utility (per flow-onboarding's own product-shape table) — no accounts, no quiz, no tour, straight to the working screen after one unavoidable ask (location). That part needed no changes. The audit found one real, user-visible bug in the weather data lifecycle: a background refresh was silently blanking the entire populated dashboard back to a loading screen, defeating the stale-data indicator built earlier this session. It's fixed and regression-tested (falsification-verified: the new test fails against the old code, passes against the new). Everything else below is a mix of confirmed strengths and named-but-unactioned gaps for you to prioritize.

Flow: First-run / location setup

Pattern source: flow-onboarding, flow-permissions · Entry point: cold app launch, no stored location

    Primary action: tap a result → picks that location and lands on the dashboard

  3. 3Dashboard (activation)

    Location is stored (localStorage), user sees their True Feel for the first time — this is the activation moment.

Flow: Push notification opt-in

Pattern source: flow-permissions · Entry point: user opens the "Heat warnings" panel on the dashboard

Steps

  1. 1Heat warnings panel (collapsed by default)

    Summary line states category + frequency upfront: "Heat warnings · daily check at dawn". Opening it reveals a labeled threshold input ("Warn when the day's high reaches (°C air)") before any ask — this doubles as the priming screen.

    Primary action: Enable heat warnings → requests Notification permission, then registers the service worker and subscribes

    If permission denied → inline message: "Notifications are blocked for this site — enable them in browser settings first."
    If on iOS and not installed to Home Screen → "Could not subscribe. On iPhone, add RealTemp to your Home Screen first."
  2. 2Enabled state

    "On — checked daily against your location." + a Turn off button, symmetric in weight and tap cost to the enable action.

    Primary action: Turn off → unsubscribes, same one tap as enabling

Flow: Weather data lifecycle (dashboard)

Pattern source: flow-empty-states, flow-errors · Entry point: any time the dashboard needs current conditions — first load, retry, or a silent background refresh

Steps

  1. 1First load

    Plain text "Reading the street…" while the initial fetch is in flight.

    Gap (not fixed): this is text-only, not a skeleton matching the dashboard's actual shape (hero number, ledger rows, toggles, gauge, timeline). flow-empty-states is explicit that dashboards should skeleton, not spinner-or-text, for 1–10s waits. Real-world load times observed this session are mostly sub-1s, so the practical impact is small — but the retry-backoff path (below) can genuinely run 1.2s+, and right now that's a full-content pop-in with real layout shift. Named, not built — a skeleton is net-new UI work, not a bug fix, so it's left for you to prioritize.
  2. 2Ready

    Full dashboard: hero True Feel, math-breakdown ledger, 4 toggle groups, sweat gauge, 24h safe-window timeline, body panel, report buttons, push panel, shade map. Header shows live/stale/updating status.

  3. 3Background refresh (TTL expiry or tab refocus)

    Silently refetches when the reading passes 10 minutes old and the tab regains focus.

    Bug found and FIXED this session: the refetch used to blank the entire populated dashboard back to the plain-text loading screen the instant it started — discarding good, valid data the user was actively looking at, and defeating the "stale" badge's entire purpose (the one interaction meant to show it instead hid everything). This is flow-empty-states' anti-pattern table by name: "Refresh that blanks existing content." Root cause: loading was derived from a request key that changed on every refetch attempt, with no separate signal for "data exists but a refresh is in flight." Rewrote useWeather so the displayed data is keyed on location only, and fetch-in-flight is a separately derived flag (isRefreshing) that never hides existing content — plus a failed background refresh now silently keeps the old good data instead of replacing it with an error. Header now reads "updating…" during a live refresh instead of vanishing. Falsification-verified: the new regression test fails against the pre-fix hook (confirmed by literally reverting the file and re-running) and passes against the fix — not just written-and-hoped-green.
  4. 4Error (fetch failed)

    Distinct red-bordered box, never the same visual as loading or ready. Copy: "Weather data is momentarily unreachable. Tap retry — it usually clears in seconds." + Retry button.

    Underlying fetch already retries automatically (3 attempts, 300ms/900ms backoff) before this screen ever shows — a real production bug (Open-Meteo transient failure misreported by the browser as a CORS block) was root-caused and fixed earlier this session.

Flow: Shade map data lifecycle

Pattern source: flow-empty-states, flow-errors · Entry point: user opens the "Shade nearby" panel

Steps

  1. 1Panel opened

    Fetches nearby building footprints from OpenStreetMap Overpass on first open only (cached 30 days after).

  2. 2Error (mirror exhausted)

    "Building data is overloaded right now — it happens; try again in a minute." + Retry button. Root cause (public Overpass instances 504ing without CORS headers, misread as a generic network failure) was diagnosed and fixed earlier this session with a 3-mirror rotation + timeout + local cache.

  3. 3Ready

    Figure/ground SVG: building footprints + live sun-cast shadows for the current minute.
